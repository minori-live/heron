# ADR-NNNN: Decision title

- Status: Proposed
- Date: YYYY-MM-DD
- Owners: project maintainers
- Maintainer direction: creation request; explicit acceptance if Accepted; link when available
- Scope: current implementation, accepted future design, or proposal
- Current specification: link the owning architecture, interaction, or feature document
- Related: issue or pull request when available

## Context

Explain why future maintainers need to revisit this choice independently and
what makes reversal costly. Include only constraints needed to understand the
long-term tradeoff.

## Decision

State the durable choice (use "Proposed decision" while proposed). Name the
ownership, boundaries, or commitments it establishes. Keep current field details,
implementation stages, and temporary fixes in their owning documents or PRs.

## Alternatives considered

Name the realistic alternatives, their benefits, and the reasons for this choice.
Do not invent alternatives solely to fill the template.

## Consequences

Describe benefits, costs, and lasting constraints. Link relevant validation
evidence and delivery tracking instead of copying test plans or progress logs.

## Reconsider when

State the new evidence or constraint that would justify revisiting this choice.
A replacement ADR is created only at a maintainer's explicit request.
